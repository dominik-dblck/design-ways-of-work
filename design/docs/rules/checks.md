# Checks

Which tool holds a rule, and what keeps the tools one system.

| Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | Gate                                                          | Exceptions                                                                                                                        | Why                                                                                                                                       |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| A rule is held by the tool that reads its kind of fact: what one TypeScript file shows by ESLint (a rule or a shape of the way of working's plugin, reported as the code is written); what needs many files, running code or a file that is not TypeScript by a test, shared when the rule is; a folder, a path and a file's case by ls-lint, a name's pattern (its purpose, its prefix, its drawer's suffix) by ESLint, an unused export or file by knip, a guarantee of the language by tsc, a generated file by its generator's check mode.                    | `review`                                                      | —                                                                                                                                 | A rule reported where the code is written is fixed in the same place; each kind of fact has the one tool that reads it.                   |
| A rule across files is an ESLint rule only when it indexes the program once (`wow/one-home-per-name`); any other is a shared test.                                                                                                                                                                                                                                                                                                                                                                                                                                | `review`                                                      | —                                                                                                                                 | ESLint reads one file at a time; an index built once a run is the one read across files it holds cheaply.                                 |
| A rule is one row naming its one gate, in `shared/rules/` when it is generic and in the product's rules when not; a rule moving between gates names until when.                                                                                                                                                                                                                                                                                                                                                                                                   | `everyRuleHasAGate`                                           | —                                                                                                                                 | Two gates for one rule drift apart, and a rule with none holds nothing.                                                                   |
| A repository names its code once, in its `scope.ts` (a `RepoScope`): its ESLint config, its shared tests and its tools read that one file, and a field holds one list for one job.                                                                                                                                                                                                                                                                                                                                                                                | `tsc` · `review`                                              | —                                                                                                                                 | A list written twice drifts, and lint and a test then disagree on what a file is.                                                         |
| A tool takes its exceptions one way, the same in every repository: ESLint a directive with its reason (`comments.md`) or `eslint-suppressions.json`, a test the way of working's one baseline (`tests.md`), prettier the scope's `tables` (a row one line, its file data alone) and `unformatted` (each with its why), read by `prettier.config.ts`, and written into `.prettierignore` by `format:files`; never a list a check invents for itself, and never a `// prettier-ignore`.                                                                             | ESLint `require-description` · `review`                       | —                                                                                                                                 | What is let through is found in one place, in every repository.                                                                           |
| A lint rule or shape of the way of working is proven by its RuleTester cases, those that must fire and those that must pass, one for each case of the test it replaced.                                                                                                                                                                                                                                                                                                                                                                                           | `review`                                                      | the way of working's own `test:rules` runs them, in its repository                                                                | A gate never seen red is no gate.                                                                                                         |
| A finding says in one sentence what a person writes instead, names its rule file (`(docs/rules/names.md)`), and points at what it fired on.                                                                                                                                                                                                                                                                                                                                                                                                                       | `review`                                                      | the way of working's own `test:rules` reads each message                                                                          | The fix is made where the finding is read.                                                                                                |
| Code meets SonarJS's recommended rules too, less those `shared/lint/sonarRules.ts` turns off, each with its reason: `OFF` everywhere, `OFF_IN_TESTS` in tests.                                                                                                                                                                                                                                                                                                                                                                                                    | ESLint `sonarjs/*`                                            | `code-eval` in a file that runs code the project built, each named in the scope's `runsCode` with its why                         | It reads what a reviewer misses: a regular expression that backtracks, a value written and never read, a collection that is always empty. |
| Every word the scope's `spelling` names is spelled (cspell, `en` and `en-GB`, another language only in the files it names); a word no dictionary holds has one home: the way of working's (`shared/lint/wowWords.ts`) or the product's, built from its data where data names it, never an inline directive.                                                                                                                                                                                                                                                       | `lint:words` · `theSpellingNamesFiles`                        | a test, until data names its people and its translations' words; a generated file, spelled at its source                          | A misspelt word on a screen is found as it is typed, not when someone reads it there.                                                     |
| Every dependency is pinned to one exact version, the same in every `package.json` syncpack reads: the root's and those its `workspaces` name (`shared/lint/syncpackConfig.ts`).                                                                                                                                                                                                                                                                                                                                                                                   | `lint:deps`                                                   | —                                                                                                                                 | A range lets two installs of one commit differ: a check green on one machine is red on the next.                                          |
| The data both sides hold (the groups a repository's scope names: shapes, tokens, words) is compared in one form at a feature's end: `sync:groups` (`shared/sync/`) reads the agreed form, the release's and the build side's code, and reports each group moved, leaf by leaf, with the side that moved it; it reports, never refuses, and each difference is decided, taken into the spec or put back, and recorded.                                                                                                                                             | `review` (answer-cc reads the report and files each decision) | until its port: its forms emitted by its build, each group's projection agreed with the build side, the event payloads once typed | The build side builds as it needs and the spec stays the source: a run’s drift is seen once, at its end, never blocking a question.       |
| A tool the checks load through another (ESLint, TypeScript, Vitest, typescript-eslint and every package of its scope) resolves to one version in the lockfile.                                                                                                                                                                                                                                                                                                                                                                                                    | `aCheckToolResolvesOnce`                                      | —                                                                                                                                 | Two copies, and a check proves its rule on one while the code runs on the other.                                                          |
| A commit message is a subject of at most 72 characters, every character counted, closed by no full stop, and one blank line before any body (`shared/lint/commitlintConfig.ts`); its words are each side's own.                                                                                                                                                                                                                                                                                                                                                   | `lint:commit` (commit-msg)                                    | a merge commit, as git writes it                                                                                                  | A subject is read whole in one line of a log, and what follows one blank line is what git and every tool read as the body.                |
| A generator writes its own files alone: run under `--permission`, it may write only to the `--out` its scope names.                                                                                                                                                                                                                                                                                                                                                                                                                                               | `aGeneratedFileIsAFreshEmit`                                  | —                                                                                                                                 | A generator that reaches past its files can overwrite another's, and nothing would say which wrote what.                                  |
| A check writes only the outputs its scope names, each with its why (a build-info file, a report folder, the test database it resets), and no other check reads them.                                                                                                                                                                                                                                                                                                                                                                                              | `review`                                                      | until a stamp test: a run, then nothing newer outside the named outputs                                                           | A check that writes elsewhere leaves state the next run reads: a result that depends on the order the checks ran in.                      |
| Nothing happens by default: a generator names its files, a baseline starts by its own act, a scope field has no default, and a script's flag that chooses where it writes or what it reaches (`--out`, `--for`) is required.                                                                                                                                                                                                                                                                                                                                      | `tsc` · `baseline`                                            | a flag's clause is `review` until a scan reads the scripts' flags                                                                 | A default does its work unseen: the reader of a call cannot tell where it wrote or what it touched.                                       |
| Every check runs at a tier of one map (`shared/checkTiers.ts`), the same on both sides: as a file is written, on that file (the edit hook: Prettier, ESLint with SonarJS, cspell); at a commit (`check:chunk`), on the files it stages, and at a merge commit on what it brings, beside the whole program's type check and the tree's checks of seconds, in under 3 minutes; at a feature's end and a push (`check:feature`), on the whole tree. A check too slow for its tier moves to the next, never out: a script no tier and no git hook runs gates nothing. | `everyRuleHasAGate` · `check:chunk` · `check:feature`         | —                                                                                                                                 | A commit waits only on what it touches, so the work stays fast, and the whole tree still passes before a feature is done.                 |
| A `spike/*` branch runs neither tier: a prototype is tried there freely; merged, a merge commit runs the commit tier on what it brings and the push the feature end on the whole tree, so a fast-forward's work is checked at the push.                                                                                                                                                                                                                                                                                                                           | `check:chunk` (it skips a spike) · `review`                   | —                                                                                                                                 | Work is fast where it is tried; the gates hold what reaches the integration branch.                                                       |
| The way of working names no product: a blank repository spawned from its template, with an empty `scope.ts` and an empty rules file, passes every shared check from its first day.                                                                                                                                                                                                                                                                                                                                                                                | `theWayOfWorkingNamesNoProduct` · `review`                    | the spawn check comes with the template (phase 7)                                                                                 | What a product needs is its own; the way of working is the same for every product.                                                        |
